# Releasing Otium

How Otium is versioned, released and supported, for whoever cuts a release. It follows the
[Release Management GuideBook](https://github.com/rollerscapes/Release-Management-GuideBook) for
versions and support, and GitHub's release practice
([Zero to Hero](https://zerotohero.dev/inbox/github-releases/),
[Mastering GitHub Releases](https://medium.com/@pracasupreti/mastering-github-releases-a-complete-guide-to-release-management-7bece85616cd))
for publishing. It is trimmed to what one maintainer can keep up; where it departs from a source,
it says so.

## Versions

The version lives in one place, `otium.versionName` in `gradle.properties`. Everything else
follows from it:

- **Semantic Versioning.** `MAJOR.MINOR.PATCH`, starting at 1.0.0. For an app the "public API"
  is what users rely on, so:
  - **MAJOR** when users lose something they had: an older backup no longer restores, a feature
    is removed, or the minimum Android version goes up;
  - **MINOR** for new features and changes that keep existing data and backups working;
  - **PATCH** for fixes only.

  The guidebook keeps an app on 0.x until it is stable. Otium starts at 1.0.0 instead, because
  the version 1 features are complete and its backups and database are already a contract to
  keep.
- **Stages.** An optional stage written in full and in capitals, numbered from 1: `ALPHA`, `BETA`,
  `RC` (`1.0.0-BETA2`). `ALPHA` is for developers and may be broken, `BETA` is usable by early
  testers, and `RC` takes bug fixes only. There is no `STABLE` label; no stage means stable.
- **Tags.** The tag is the version with a lowercase `v`: `v1.0.0`, `v1.1.0-RC1`. Tags are
  annotated, and a tag is never moved, deleted or reused, and neither is a version number, even
  for a broken release.
- **versionCode** is computed from the version in `app/build.gradle.kts`, so Play always sees a
  higher code for a later version:

| Version | Formula | versionCode |
|---------|---------|-------------|
| `1.0.0` | 1 × 1,000,000 + 99 | 1000099 |
| `1.0.1` | 1,000,000 + 1 × 100 + 99 | 1000199 |
| `1.1.0-BETA2` | 1,000,000 + 1 × 10,000 + 30 + 2 | 1010032 |
| `1.1.0-RC1` | 1,000,000 + 10,000 + 60 + 1 | 1010061 |
| `1.1.0` | 1,000,000 + 10,000 + 99 | 1010099 |
| `2.0.0` | 2 × 1,000,000 + 99 | 2000099 |

Minor and patch go up to 99, and a stage number up to 29; the build refuses anything else.

## What a release contains

The [release workflow](../.github/workflows/release.yml) runs when a version tag is pushed. It
checks that the tag matches `otium.versionName`, that the tagged commit is on `main`, and that
`CHANGELOG.md` has a section for the version. It runs the unit tests and Android Lint, builds with
the upload key from the `release` environment, and creates a **draft** GitHub release titled
`Otium v<version>` with these files:

| File | What it is |
|------|------------|
| `otium-<version>.aab` | The bundle for Google Play |
| `otium-<version>.apk` | The APK, signed with the upload key, for installing by hand |
| `otium-<version>-mapping.txt` | The R8 mapping, to read stack traces from the release build |
| `otium-<version>-sbom.cdx.json` | The CycloneDX SBOM of the shipped dependencies |
| `SHA256SUMS` | Checksums of the files above |

Every file has a signed build provenance attestation that ties it to the workflow run and the
commit. The release notes have three parts:

1. The version's section of [CHANGELOG.md](../CHANGELOG.md): what changed for users.
2. How to install the APK and verify a download.
3. The pull requests since the previous release, with their authors and first-time contributors,
   generated by GitHub and grouped by label as set in `.github/release.yml`.

Versions with a stage (ALPHA, BETA, RC) are pre-releases, which GitHub never shows as the latest
release. A stable version becomes the latest by its version number.

Anyone can check a download:

```bash
sha256sum --check --ignore-missing SHA256SUMS
gh attestation verify otium-1.0.0.apk --repo eh0x/otium
```

The GitHub APK and an install from Play are signed with different keys (Play re-signs with its
app signing key), so one cannot update the other; a tester switching over uninstalls first. Drive
sign-in needs an OAuth client for each of the two certificates (see `keystore.properties.example`).

Uploading the bundle to Play is not automated yet. Upload `otium-<version>.aab` to the internal
testing track in the Play Console by hand.

## Writing the changelog

The changelog is for people who use the app, not a commit log; the generated pull request list
covers that. Every pull request that changes what users see adds a line under `[Unreleased]`:

- Group lines under Security, Added, Changed, Deprecated, Removed and Fixed, in that order, as in
  [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) with Security moved first.
- Say what changed and why it matters, in the user's words. When users must act (re-enter a
  passphrase, update before restoring a backup), say so first, in bold.
- Breaking changes go under Changed or Removed, with what to do instead.
- Known problems go in a short paragraph at the top of the version's section.

## Cutting a release

Release from `develop` through `main`, with CI green at each step:

1. On a branch from `develop` named `chore/release-<version>`:
   - set `otium.versionName` in `gradle.properties`;
   - in `CHANGELOG.md`, move the entries under `[Unreleased]` to a new `## [1.1.0] - YYYY-MM-DD`
     section and update the compare links at the bottom;
   - commit as `chore(release): prepare 1.1.0`.
2. Open a pull request into `develop` and merge it.
3. Open a pull request from `develop` into `main` and merge it once the checks pass.
4. Tag the merge commit on `main` and push the tag:

   ```bash
   git fetch origin
   git tag -a v1.1.0 -m "Otium v1.1.0" origin/main
   git push origin v1.1.0
   ```

5. Follow the run under Actions, Release, or with `gh run watch`. When it fails because of the
   code or the build, fix the cause through a pull request and tag a new version; do not move the
   tag. When it fails for an outside reason (a runner or network error), re-run it.
6. Test the draft before anyone can see it: download the APK from the draft release, install it
   on a device, and run the [release smoke test](../CONTRIBUTING.md#testing). Read the notes and
   fix them in the draft if needed. If the files are wrong, delete the draft (the tag stays), fix
   the cause and tag a new version.
7. Publish it, which also opens an announcement in Discussions:

   ```bash
   gh release edit v1.1.0 --draft=false --discussion-category Announcements
   ```

8. After publishing, check that the download links work, that the downloaded files pass the
   checks in [What a release contains](#what-a-release-contains), and upload the bundle to Play.

Keep releases small and frequent: a release ships what is ready, and anything unfinished waits for
the next one. Leave at least a day between stages of the same version (BETA, RC, stable).

## Fixing a released version

When `develop` already holds work that should not ship yet, a fix for the latest release starts
from its tag:

1. Branch from the tag: `git switch -c fix/<what> v1.1.0`.
2. Fix it, set `otium.versionName` to `1.1.1`, and add a `## [1.1.1]` section to the changelog.
3. Open a pull request into `main`, merge it, then tag `v1.1.1` and release it as above.
4. Merge `main` back into `develop` through a pull request, so the fix is not lost.

When `develop` holds nothing unreleased, cut a normal release instead.

## Broken and security releases

A release is broken when it cannot be used or its metadata is wrong: it crashes on start, a check
was skipped, it shows the wrong version, it raises the minimum Android version in a minor or patch
release, or a dependency brought in a vulnerability. A published release is never deleted or
changed in place; with immutable releases on, its files and tag cannot change anyway. Instead:

1. Add `[YANKED]` to its GitHub release title and its changelog heading
   (`## [1.1.0] - 2026-11-02 [YANKED]`), with one line in its notes saying why and which version
   to use.
2. Ship the fix as a new version.

A release that fixes a vulnerability gets `[SECURITY RELEASE]` at the start of its title, its fix
listed under Security in the changelog, and a security advisory as described in
[SECURITY.md](../SECURITY.md):

```bash
gh release edit v1.1.1 --title "[SECURITY RELEASE] Otium v1.1.1"
```

## Supported versions

Only the latest release receives fixes, bug fixes and security fixes alike. This departs from the
guidebook's maintenance periods on purpose: Otium is an app that updates itself from the store,
not a library that others pin, and it has one maintainer. [SECURITY.md](../SECURITY.md) states the
same.

## One-time setup

Done once per repository by an admin, before the first tag:

1. **Upload key.** Create it as described in `keystore.properties.example`, and back it up.
2. **Environment.** In Settings, Environments, create `release`. Under deployment branches and
   tags, allow only tags matching `v*`. Optionally add the maintainer as a required reviewer, with
   "Prevent self-review" off, to get a pause before the key is used.
3. **Secrets** in the `release` environment, not in the repository:

   | Secret | Value |
   |--------|-------|
   | `UPLOAD_KEYSTORE_BASE64` | The keystore file, base64-encoded (`base64 -i <file>.jks`) |
   | `UPLOAD_STORE_PASSWORD` | The store password |
   | `UPLOAD_KEY_ALIAS` | The key alias, for example `upload` |
   | `UPLOAD_KEY_PASSWORD` | The key password |

   The passwords go into a properties file, so avoid backslashes in them.

4. **Tag ruleset.** In Settings, Rules, add a tag ruleset for `refs/tags/v*` that restricts
   creation, update and deletion to admins, so only a maintainer can start a release and no
   release tag can move.
5. **Immutable releases.** In Settings, General, Releases, turn on release immutability. A
   published release's files and tag are then locked; its title and notes can still be edited.
6. **Labels.** Create a `security` label, so security fixes get their own group in the generated
   notes. The other groups use the existing labels.
7. **Play App Signing.** When the app is created in the Play Console, enrol in Play App Signing
   and register the upload key's certificate.
